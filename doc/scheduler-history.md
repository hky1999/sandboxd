# Scheduler history reclamation

`CollectHistory` is an extension on the existing private sandbox service control socket. The caller is the trusted node agent that owns this daemon namespace. It supplies a Coordinator catalog boundary and a batch of no more than32 original operations. The call acknowledges history processing only; it never invokes runtime deletion, changes resources, returns a retirement generation, or authorizes budget release. Production acceptance and deployment identities belong to the consuming scheduler ledger.

The boundary names the control authority, Coordinator epoch, global allocation generation and catalog revision. It retains each referenced assignment and its minimum permitted Runtime revision. These ordered coordinates only close previously established ownership; they never prove physical identity. Rollback, authority changes, reopening a closed assignment and conflicting views of the same catalog revision are rejected. Active and unknown physical operations retain their original facts.

New start operation UUIDs use UUID version8 derived from SHA256 over length-prefixed UTF-8 strings: `sandboxd-history-start-v1`, authority, environment ID, Runtime ID, decimal assignment generation and full request fingerprint. Each length is unsigned big-endian64 bits. The first16 digest bytes receive UUID version8 and RFC variant bits. The daemon independently checks the binding and the actual start labels. Existing legacy admissions remain queryable; after a boundary is installed, an absent legacy operation cannot be admitted or sealed as non-creation. A closed qualified operation is likewise rejected.

For an admitted operation, reclamation requires its complete original fingerprint and deadline and either durable NOT_CREATED or a matching completed physical retirement receipt and all eight original cleanup steps. Original metadata binds the environment, Runtime, assignment generation, sandbox ID and resource generation. A different live generation with the same sandbox ID is preserved. The receipt, progress and matching allowlisted resource observations are removed only for the selected original generation. Original metadata may contain sensitive configuration and is never copied into the reclamation manifest or responses.

`<RootDir>/scheduler-start-operations.history` persists the boundary and bounded pending deletion manifest. It records only owned relative paths, original directory and file device/inode, size and SHA256. The manifest and its parent directory are synced before the first unlink. The admission index is durably upgraded to `sandboxd-start-operations-v2` before deletion; older daemons refuse that index. A missing or corrupt boundary with a version2 index fails closed. Each unlink uses the selected original private directory and rechecks its file identity. Completed pairs are removed from a rewritten, synced admission index. Restart resumes the same manifest, and a lost acknowledgment can replay history collection. Unknown or changed records prevent the affected transaction from completing.

Limits remain65536 admitted operations,64KiB per start record,4MiB per original progress record,8MiB for boundary/manifest state and32 candidates plus4096 files per transaction. An oversized manifest is rejected before replacing the durable boundary. Protected assignments and unknown results may retain state indefinitely; capacity exhaustion requires reconciliation and never permits forgetting them. Source request bytes and environment values are not persisted in the new manifest.

These contracts assume persistent daemon-owned storage and its fsync promises. Missing disks, simultaneous rollback of authoritative stores to a consistent old backup, and arbitrary storage tampering require external isolation and a new authority; an internal boundary cannot establish an external nonrollback watermark.

## Unpublished temporary files

Temporary history files never authorize admission, retirement, or budget release. After validating the authoritative index and history sidecar, the daemon discards only its unpublished `.history-<uint32>` files. It pins the original parent directory for the journal lifetime, verifies the original admission directory, index and flock paths, and removes unchanged, owner-only 0600 regular files with one link and at most 8 MiB through that parent descriptor. Special permission bits, replaced paths and a missing existing lock fail closed. Foreign names remain untouched.

Directory entries are read in batches of 128 to bound memory use. This does not promise a strict upper bound on total scan time. Partial temporary bytes are discarded without interpreting them as authority; missing or corrupt authoritative state still refuses startup. A retained original disk and its filesystem durability contract remain required.
